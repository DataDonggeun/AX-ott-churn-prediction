## 1. 프로젝트 개요

### 목적
OTT 신규 구독자의 가입 후 21일(day0~day20) 시청 행동 데이터를 분석하여 이탈 가능성이 높은 유저를 예측하고 세그먼트별 맞춤 CRM 전략을 도출한다.

### 데이터
- 학습: 23,081명 (Membership_train.csv)
- 테스트: 2,545명 (Membership_test.csv)
- 관측 기간: 가입 후 21일 (day0~day20)
- 예측 목표: **이탈 여부 (이탈=1, 재구매=0)** ← `y = 1 - is_repurchase` 로 변환

### 최종 모델 (2026-06-02 기준)
- 모델: XGBoost (Optuna 30 trial 튜닝 완료)
- 전체 AUC: 0.8789
- 프로모션 AUC: 0.8636
- 비프로모션 AUC: 0.8853

## 1-1. 주요 코드 변경 이력 (2026-06-02)

| 항목 | 변경 전 | 변경 후 | 영향 파일 |
|---|---|---|---|
| **모델 타겟** | `y = is_repurchase` (재구매=1) | `y = 1 - is_repurchase` (이탈=1) | step04, 06, 07, 08, 09 |
| **step08 출력** | `churn_risk = 1 - score` | `churn_risk = score` (직접) | step08 |
| **step04 모델 추가** | LR / XGBoost / RF | LR / **SVM** / XGBoost / RF | step04 |

> **타겟 변경 이유**: 성능(AUC)은 동일하지만 모델이 이탈 확률을 직접 출력하도록 해 `churn_risk = score`로 단순화. SHAP 방향도 이탈=양수로 직관적으로 맞춰짐.

> **캐시 주의**: 타겟 변경 후 기존 pkl 모델은 재사용 불가. 반드시 `run-full` 재실행 필요.

## 5. 모델 선정 과정

### step04 — 계열 선정
- 비교: LogisticRegression / **SVM** / XGBoost / RandomForest (SVM 2026-06-02 추가)
- 기준: ROC-AUC 성능 + train_valid_gap (과적합)
- 결과: XGBoost 전 scope 1위 → boosting 계열 확정
- SVM 탈락 이유: gap 0.065~0.084 (과적합)
- RandomForest 탈락 이유: gap 0.05 초과

### step06 — 최종 모델 선정
- 비교: LightGBM / HistGB / CatBoost / GradientBoosting / XGBoost
- 기준: gap ≤ 0.03 필터 → 통과한 모델 중 가장 많이 1등한 모델 → 통합 모델
- 결과: **XGBoost** 선정 (2026-06-02 기준, 타겟 이탈=1로 변경 후)
- GradientBoosting도 경합했으나 XGBoost 최다 1등

### step07 — 하이퍼파라미터 튜닝 (2026-06-02, XGBoost 30 trial)
| Scope | 튜닝 전 | 튜닝 후 | 향상 |
|---|---|---|---|
| overall | 0.8624 | 0.8789 | +0.0165 |
| promotion_only | 0.8453 | 0.8636 | +0.0183 |
| nonpromotion_only | 0.8687 | 0.8853 | +0.0166 |

### 코드 노드 설정
- 입력 변수: `raw` → HTTP 요청 노드의 `body` 연결
- 출력 변수: `context` (String)
```python
import json

def main(raw: str) -> dict:
    data = json.loads(raw)

    step10 = data.get("step10", {})
    step09 = data.get("step09", {})
    step07 = data.get("step07", {})

    # 세그먼트
    segs = step10.get("segments", [])
    seg_text = ""
    for s in segs:
        seg_text += (
            f"{s['segment']}: {s['row_count']}명 ({round(s.get('row_share',0)*100,1)}%) "
            f"재구매율={s.get('repurchase_rate','?')} 이탈위험={s.get('mean_churn_risk','?')}\n"
        )

    # SHAP
    shap_list = step09.get("by_scope", {}).get("overall", {}).get("shap", {}).get("top20", [])
    shap_text = ""
    for i, f in enumerate(shap_list[:10], 1):
        shap_text += f"{i}. {f['feature']} ({f.get('mean_abs_shap', 0):.5f})\n"

    # AUC
    auc_text = ""
    for scope, info in step07.get("by_scope", {}).items():
        auc_text += f"{scope}: {info.get('tuned_auc', '?')}\n"

    return {
        "context": f"=== 세그먼트 현황 ===\n{seg_text}\n=== SHAP 상위 10 피처 ===\n{shap_text}\n=== 모델 AUC ===\n{auc_text}"
    }
```

## 15. 변경 이력 (2026-06-02)

### GradientBoosting 제거 (step06, step07)
- **이유**: GradientBoosting은 trial당 1~4분 소요 → 900초(15분) timeout 내 6~11 trial밖에 못 돌림. 탐색이 너무 제한되고 속도 대비 성능 이득 없음
- **step06.py**: `FAMILY_MAP["boosting"]`에서 `GradientBoosting` 제거, `_build_models()`에서 제거, import 제거
- **step07.py**: `_make_model()` / `_search_space()`에서 `GradientBoosting` 케이스 제거, import 제거
- **재실행 필요**: step06 force=true → step07 force=true → step08 → step09 → step10 순서로 재실행

### step07 최신 결과 (XGBoost 선정, 30 trials 완료)
- 이전 인수인계의 CatBoost 결과와 다름 — step06 재실행 후 XGBoost가 선정됨
- **재실행 필요 시 CatBoost가 다시 선정될 수도 있음** (GradientBoosting 제거로 순위 바뀔 수 있음)

| Scope | 모델 | 튜닝 전 AUC | 튜닝 후 AUC | 향상 | trials |
|---|---|---|---|---|---|
| overall | XGBoost | 0.8624 | 0.8789 | +0.0165 | 30 |
| promotion_only | XGBoost | 0.8453 | 0.8636 | +0.0183 | 30 |
| nonpromotion_only | XGBoost | 0.8687 | 0.8853 | +0.0166 | 30 |

### Optuna 구조 메모
- `StratifiedGroupKFold(k=5)` × 30 trials = scope당 150번 학습
- `timeout=900s(15분)` per scope — GradientBoosting처럼 느린 모델은 trial 수가 크게 줄어듦
- `TPESampler(seed=RANDOM_STATE)` 고정 → study 새로 생성할 때마다 trial 0의 파라미터가 항상 동일하게 시작
- train/valid/test 분리 없음 — expanded_dataset.csv 전체를 k-fold로만 사용

### 향후 추가 예정: Membership_test.csv 최종 평가

- step00에서 Views_test.csv + Membership_test.csv feature engineering → tuned_model.pkl로 predict → AUC 비교
- **주의**: test set은 딱 1회만 사용. 결과 보고 재튜닝하면 leakage

### 에이전트 판단 기준 (단 하나)

> **"LLM이 다음 행동을 스스로 결정하는가?"**
>
> YES → 에이전트 / NO → 파이프라인

---

### 현재 시스템의 정확한 분류

| 컴포넌트 | 분류 | 이유 |
|---|---|---|
| Dify 워크플로우 "OTT 파이프라인 실행기" | **파이프라인** | HTTP 호출 순서가 코드에 고정, LLM은 마지막에 텍스트만 생성 |
| Dify Chatflow "OTT 이탈 분석 어시스턴트" | **파이프라인** | HTTP → Code → LLM 순서 고정, LLM이 흐름을 결정하지 않음 |
| LangGraph agent.py | **파이프라인** | `add_edge`만 사용, 흐름이 코드에 고정, 조건 분기 없음 |
| Streamlit app.py | **파이프라인** | LangGraph를 고정 순서로 호출 |

**요약: 현재 시스템은 전체가 파이프라인이며 에이전트가 없음.**

---

### 진짜 에이전트로 만드는 방법

#### 방법 A: Dify Agent 타입 — 단일 에이전트

cloud.dify.ai에서 **Workflow/Chatflow가 아닌 "Agent" 앱 타입**을 선택하면 진짜 에이전트가 됩니다.

**구현 방법:**
1. Dify → 새 앱 → **Agent** 타입 선택
2. FastAPI 엔드포인트를 커스텀 도구로 등록:
   - `GET /pipeline/report/json` → 전체 분석 결과
   - `GET /pipeline/status` → 파이프라인 상태
3. 시스템 프롬프트 작성 (도구 선택 기준 명시)
4. 완료

**왜 진짜 에이전트인가:**
```
사용자: "S6 이탈 원인 분석해줘"

LLM 판단: 세그먼트 데이터 필요 → get_segments 호출
LLM 관찰: S6 4,846명, 이탈위험 50.2%
LLM 판단: 원인을 알려면 SHAP 필요 → get_shap 호출
LLM 관찰: retention_w3_ratio 1위
LLM 판단: 충분함 → 최종 답변 생성

← 매 단계를 LLM이 결정 (ReAct 패턴)
```

**한계:** 단일 에이전트. 병렬 전문가 실행 없음.

---

#### 방법 B: LangGraph conditional edges — 멀티에이전트

agent.py에 `add_conditional_edges`를 추가하면 목표 다이어그램의 멀티에이전트 시스템이 됩니다.

**핵심 변경사항:**
```python
# 현재 (파이프라인)
g.add_edge("load", "parallel")
g.add_edge("parallel", "action")
# → 흐름이 코드에 고정

# 변경 후 (진짜 에이전트)
def route_after_judge(state) -> str:
    if state["judge_verdict"] == "sufficient" or state["iteration"] >= 2:
        return "final_report"
    return "supervisor"  # LLM 판단에 따라 재계획

g.add_conditional_edges("judge", route_after_judge, {
    "final_report": "final_report",
    "supervisor": "supervisor"   # ← 루프 발생, 진짜 에이전트
})
```

**달성 가능한 구조:**
```
Supervisor (LLM 계획 수립)
    ↓ 병렬
[Specialist 1~5] (각자 다른 시스템 프롬프트)
    ↓
Judge (LLM 품질 평가)
    ↓
조건 분기: 충분 → 보고서 / 부족 → Supervisor 재계획 (루프)
```

---

### 방법 비교

| | Dify Agent 타입 | LangGraph conditional |
|---|---|---|
| 에이전트 여부 | ✅ 단일 에이전트 | ✅ 멀티에이전트 |
| 구현 난이도 | 낮음 (1~2시간) | 중간 (1~2일) |
| 병렬 실행 | ❌ | ✅ ThreadPoolExecutor |
| Supervisor/Judge 분리 | ❌ | ✅ |
| 재계획 루프 | ✅ (ReAct 내장) | ✅ (conditional edges) |
| 목표 다이어그램 일치 | 절반 | 완전 |

---

### 중요: Chatflow 병렬 LLM은 에이전트가 아님

Chatflow에 LLM 노드를 5개 병렬로 넣어도 에이전트가 아닙니다.
- LLM이 텍스트를 생성하지만 실행 흐름을 제어하지 않음
- 그래프 구조(코드)가 5개 모두를 항상 실행
- "멀티 LLM 파이프라인"이라고 부르는 게 정확함

---

### 권장 구현 순서

1. **즉시 (1~2시간)**: Dify Agent 타입 앱 신규 생성 → 단일 에이전트 완성
2. **이후 (1~2일)**: agent.py에 `add_conditional_edges` 추가 → 멀티에이전트 완성
3. **최종**: Dify는 UI/인터페이스, LangGraph가 에이전트 로직 담당

## 20. 에이전트 판단 구간 (개선안)

파이프라인 결과를 보고 LLM이 다음 행동을 결정하는 구간.

### 1구간 후 (EDA + 베이스라인 완료)
```
LLM 판단 가능한 것:
- "프로모션/비프로모션 이탈률 차이가 크다 → scope 분리 학습 강화"
- "VIF inf 피처가 많다 → 피처 제거 후 step00 재실행"
- "베이스라인 AUC가 0.75 이하다 → 피처 엔지니어링 재검토"
```

### 2구간 후 (OOF 생성 완료)
```
LLM 판단 가능한 것:
- "XGBoost와 CatBoost OOF 상관관계 0.95 → 하나 제외"
- "RF gap 0.089 → 포함 여부 판단"
- "Meta AUC < Base 최고 AUC → 스태킹 효과 없음, 단일 모델 추천"
```

### 3구간 후 (SHAP + 세그먼트 완료)
```
LLM 판단 가능한 것:
- "retention 피처가 1, 2위 → 데이터 누수 가능성 검토"
- "S6 세그먼트 비율이 30% 초과 → 임계값 조정 필요"
- "SHAP 방향이 직관과 반대 → 모델 재학습 필요"
```

### Judge 루프
```
Judge LLM 평가 기준:
  충분: AUC ≥ 0.87, gap ≤ 0.05, S6 ≤ 25% → 보고서 생성
  부족: 위 조건 미달 → Supervisor에게 재계획 요청 (최대 3회)
```

## 21. 최종 설계 확정 사항 (2026-06-03)

### 모델링
```
현재: XGBoost 단일 모델 AUC 0.8789
개선: 5개 Base Learner + Meta LR 스태킹
      성능 향상 보장 없지만 내려가지는 않음

Base Learner best_params 이미 확보:
  LR:       AUC 0.8509, gap 0.0042 (가장 안정)
  XGBoost:  AUC 0.8854, gap 0.0361
  CatBoost: AUC 0.8861, gap 0.0466 (성능 1위)
  RF:       AUC 0.8681, gap 0.0891 (과적합이지만 Meta에 포함)
  SVM:      params 보유, OOF만 돌리면 됨

Optuna 불필요 (입력 4~5개뿐)
```

### 에이전트 vs 파이프라인 vs 사람
```
규칙으로 처리:
  쿨다운 (last_crm_date 체크)
  스태킹 채택 (Meta AUC > Base 최고 AUC)
  과적합 판단 (gap > 0.05)

에이전트로 처리:
  EDA 결과 보고 피처 추가/제거 판단 (A구간)
  Judge 품질 평가

사람이 처리:
```

## 23. 에이전트 vs 파이프라인 최종 결론 (2026-06-03)

### 현재 시스템의 정확한 정의

> **"결과물 품질 검증 루프가 탑재된 고도화된 멀티 LLM 파이프라인"**

LLM이 여러 개 쓰이고 Judge → Supervisor 피드백 루프가 있어도, **실행 경로의 주도권이 파이썬 코드(add_edge)에 있으면 파이프라인**이다.

### 에이전트가 되기 위한 세 가지 조건

| 조건 | 내용 | 구현 난이도 | 이 프로젝트 필요성 |
|---|---|---|---|
| Routing Hub | Supervisor LLM이 질문 보고 어떤 전문가 호출할지 결정 | 중간 | 비용 절감용으로 유용 |
| Structured Judge | Judge가 target_node 지정해서 핀포인트 루프 | 낮음 | 품질 최적화용으로 유용 |
| Tool Calling | 전문가가 직접 API 호출해서 필요한 데이터 선택 | 높음 | **현재 불필요** |

### Tool Calling이 현재 불필요한 이유

완전한 Tool Calling 에이전트가 필요한 환경: 웹 검색, DB 쿼리, 사내 문서 등 **데이터 위치가 불확실한 혼돈의 환경**

이 프로젝트의 현실: step00~10으로 데이터 계약이 완료되고 구조가 명확하다. 불확실성이 없는 곳에 불확실성 해소 도구를 가져오면 오히려 할루시네이션·비용만 증가한다.

### 실용적 구현 순서

```
1. Routing Hub   → 불필요한 전문가 호출 막는 비용 절감 필터
2. Structured Judge → 루프 범위 좁히는 품질 최적화 장치
3. Tool Calling  → 비정형 외부 데이터 유입 시점에 검토
```

### Dify 연동 최종 구조

```
[Dify 챗플로우 / 웹 UI]
    ↓ POST /agent/query (단일 HTTP 호출)
[FastAPI / LangGraph 파이프라인]
    ↓ 내부 함수 호출
[ML 파이프라인 step00~11]
```

- Dify: 사용자 채팅 인터페이스, 게이트웨이 역할만
- LangGraph: Supervisor → 전문가 병렬 → Judge 루프 내부 완결
- 스트리밍(SSE): 미적용. 동기식 응답. Gemini 2.5 Pro 기준 10~20초 내 응답 가능

### POST /agent/query 응답 규격

```json
{
  "status": "success",
  "final_answer": "...",
  "iterations": 1,
  "judge_verdict": "sufficient"
}
```

### 챗봇 코드 노드 (업데이트 버전)
```python
import json

def main(raw: str) -> dict:
    data = json.loads(raw)

    step07 = data.get("step07", {})
    step06 = data.get("step06", {})
    step05_meta = data.get("step05_meta", {})
    test_score = data.get("test_score", {})

    # 세그먼트
    segs = step07.get("segments", [])
    seg_text = ""
    for s in segs:
        seg_text += (
            f"{s['segment']}: {s['row_count']}명 ({round(s.get('row_share',0)*100,1)}%) "
            f"재구매율={s.get('repurchase_rate','?')} 이탈위험={s.get('mean_churn_risk','?')}\n"
        )

    # SHAP
    shap_list = step06.get("by_scope", {}).get("overall", {}).get("shap", {}).get("top20", [])
    shap_text = ""
    for i, f in enumerate(shap_list[:10], 1):
        shap_text += f"{i}. {f['feature']} ({f.get('mean_abs_shap', 0):.5f})\n"

    # AUC (스태킹 결과)
    auc_text = ""
    for scope, info in step05_meta.get("by_scope", {}).items():
        meta_auc = info.get("meta_auc", "?")
        adopted = "채택" if info.get("adopted") else f"미채택(fallback: {info.get('fallback','?')})"
        auc_text += f"{scope}: Meta AUC={meta_auc} ({adopted})\n"

    # Test AUC
    test_text = ""
    for r in test_score.get("by_scope", []):
        test_text += f"{r['scope']}: OOF={r.get('oof_auc','?')} / Test={r.get('test_auc','?')}\n"

    return {
        "context": (
            f"=== 세그먼트 현황 ===\n{seg_text}\n"
            f"=== SHAP 상위 10 피처 ===\n{shap_text}\n"
            f"=== 스태킹 모델 AUC ===\n{auc_text}\n"
            f"=== Test 평가 ===\n{test_text if test_text else '미실행'}"
        )
    }
```

### 개요

### 1. 개발자 보고서 (LLM_DEV) — 버그 수정 이력

#### 버그 1: 양호 행에 빨간 배경 표시

- **증상**: OOF 표에서 LR, XGBoost처럼 gap이 낮은 양호 모델 행도 빨간 배경(`.ov` class)으로 표시됨
- **원인 1차**: `is_overfit` JSON 필드를 LLM에 직접 읽히니 LR(gap=0.0032)을 과적합으로 오해
- **수정 1차**: JSON 필드 대신 `gap > 0.05` 수식 + 구체적 예시 명시

#### 버그 2: 과적합 행만 빨간색인데 짝수 번째 행만 분홍배경 표시

- **증상**: 과적합 행 중 홀수번째(CatBoost overall, CatBoost promotion…)는 배경색이 없고, 짝수번째(RF overall, RF promotion…)만 분홍 배경
- **근본 원인**: LLM이 CSS style block에 `tr:nth-child(even)` 줄무늬 스타일을 몰래 추가함
  - `.ov` + 짝수 행: nth-child specificity가 class보다 높아 분홍 배경이 덮어쓰여짐 → 빨간 배경 실종
  - `.ov` + 홀수 행: nth-child가 회색 배경 적용 → `.ov` 분홍 배경이 아예 안 보임
- **수정**: `[절대 금지]` 섹션에 `tr:nth-child(even), tr:nth-child(odd), 줄무늬 스타일 절대 추가 금지` 명시

#### 버그 3: 프롬프트로 class 규칙을 아무리 설명해도 LLM이 행 구조를 계속 잘못 생성

- **근본 원인**: LLM이 어떤 행에 `.ov` class를 붙일지 스스로 판단하는 과정에서 반복 오류 발생
- **해결**: 15개 행 HTML 템플릿을 프롬프트에 하드코딩 → LLM은 숫자(AUC값, gap값)만 채워 넣음
- **결과**: class 오류 완전 제거

#### 버그 4: SHAP 섹션 제목이 "Top 20"으로 생성됨

- **원인**: 프롬프트에 "상위 20개" 지침이 있었음
- **수정**: "상위 10개만 출력 — 11위 이하 절대 금지" 명시

#### 버그 5: SHAP 계열별 합계 KPI 카드 환각

- **증상**: 프롬프트에 없는 "SHAP 계열별 합계" 카드 섹션이 생성됨
- **수정**: `[절대 금지]`에 "SHAP 계열별 합계 카드나 추가 섹션 생성 금지" 추가

#### 버그 6: 섹션 7(Permutation Importance) 항상 잘림

- **원인**: LLM 출력이 너무 길어 Dify 토큰 제한으로 HTML 중간에서 잘림 → script block 미실행 → 차트 미표시

### 3. 경영진 보고서 (LLM_CEO) — 버그 수정 이력

#### 버그: Chart.js 가로 막대 차트 미표시

- **원인 1**: `indexAxis:'y'`를 Chart 최상위 레벨에 두면 Chart.js v3에서 무시됨
  ```js
  // 잘못된 예 (Chart.js v3에서 동작 안 함)
  new Chart(ctx, { type:'bar', indexAxis:'y', data:{...}, options:{...} });
  ```
- **수정**: `indexAxis:'y'`를 반드시 `options:{}` 내부에 넣어야 함
  ```js
  // 올바른 예
  new Chart(ctx, { type:'bar', data:{...}, options:{ indexAxis:'y', ... } });
  ```
- **원인 2**: `maintainAspectRatio:false` 사용 시 캔버스 컨테이너에 고정 높이 없으면 height=0이 되어 차트 안 보임
- **수정**: 캔버스를 `position:relative; width:100%; height:320px` div로 감싸야 함
  ```html
  <div style="position:relative;width:100%;height:320px;">
    <canvas id="chart1"></canvas>
  </div>
  ```
