note.md 06단계에서 확정한 올바른 분석 코호트예요.

원본 데이터: 23,343행 │ duration < 21일 제거 ──→ -238행 (관측창 1~3주차를 못 채운 행) │ 완전 중복 행 제거 ──→ -26행 (동일한 데이터가 반복된 행) │ 최종 코호트: 23,079행 ✅

왜 23,079를 써야 하나

에이전트 코드의 load_cohort() 함수가 이 필터를 자동으로 적용해요. Membership_v3.csv (23,343행) → 23,079행으로 정제 후 사용.

에이전트란 무엇인가

일반 AI (ChatGPT 채팅)에이전트
질문하면 대답만 함스스로 데이터를 가져와 분석하고 결과물까지 만들어냄
한 번에 끝여러 단계를 순서대로 실행
사람이 중간에 계속 개입시작만 누르면 혼자 완주

우리가 만든 에이전트 목록

에이전트노드 수역할
📊 일별 리포트7개매일 이탈 위험 고객 자동 분석 + 보고서 생성
📅 주간 보고서2개세그먼트별 주간 요약
👔 경영진 요약2개긴 보고서를 30초 분량으로 압축
💌 리텐션 알림-나이대별 맞춤 이탈 방지 메시지 생성
📺 OTTO 마스코트-미접속 기간별 표정이 바뀌는 SVG 캐릭터

에이전트 만드는 순서

1. 무엇을 자동화할지 정한다 2. 단계를 나눈다 (노드 설계) 3. 각 노드에 AI 역할을 부여한다 4. 노드를 연결한다 (LangGraph) 5. 데이터를 연결한다 (23,079 코호트) 6. UI를 만든다 (Streamlit) 7. 보안 처리한다 (.env, Windows 자격증명)
한 줄 요약

에이전트 = 데이터를 가져오고 → AI가 분석하고 → 자동으로 보고서까지 만들어주는 자동화 파이프라인. 사람이 할 일: 버튼 한 번.

05

사용 기술 상세 설명

LangChain ← AI 연결의 기초 (필수) │ └── LangGraph ← 에이전트 흐름 설계 (LangChain 위에서 작동) │ ├── Gemini AI ← 각 노드의 두뇌 ├── XGBoost ← 이탈 확률 계산 ├── TMDB API ← 영화 데이터 └── python-dotenv← 보안 Streamlit ← 결과물 화면 표시 (독립적) SVG ← OTTO 캐릭터 직접 그리기 (독립적)

① LangChain — 기반 라이브러리

비유: AI랑 대화하기 위한 "공통 언어 번역기"

AI 회사마다 사용 방법이 다른데, LangChain이 전부 같은 방식으로 쓸 수 있게 통일해줘요. 나중에 Gemini → Claude로 바꾸고 싶으면 모델 이름 한 줄만 수정하면 됨.

② LangGraph — 에이전트 흐름 설계도

비유: "업무 순서도를 코드로 그리는 도구" (LangChain 위에서 작동)

노드들을 연결하는 순서도를 코드로 작성해요. 우리는 ThreadPoolExecutor로 병렬 실행도 구현 → 30초 → 15초로 단축.

③ Gemini 2.5 Flash — 실제 AI 두뇌

각 노드마다 온도(temperature)를 다르게 설정:

노드온도이유
이탈분석 노드0.1 (낮음)냉철하고 정확하게
리텐션 메시지 노드1.2 (높음)창의적이고 다양하게

④ XGBoost — 이탈 예측 모델

23,079명 데이터 학습 → 고객별 이탈 위험 확률(0~100%) 계산. 핵심 변수: watch_time_w3 (3주차 시청시간). AUC: 0.83.

⑤ Streamlit — 화면 UI

Python 코드 몇 줄로 웹 화면 생성. HTML/CSS/JavaScript 불필요. 우리가 만든 탭: 일별 리포트 / 주간 보고서 / 영화 추천 챗봇 / OTTO 마스코트.

⑥ TMDB API — 영화 추천

전 세계 영화 데이터베이스 API. 고객 시청 장르 → TMDB에서 한국 인기작 조회 → Gemini가 "추천 이유" 문장 생성.

⑦ python-dotenv + .env — 보안

API 키를 코드 안에 직접 쓰지 않고 .env 파일에 보관. .gitignore에 등록해서 GitHub에 절대 올라가지 않게 처리.

한 줄 요약

LangChain이 재료라면, LangGraph는 조립 설명서, Gemini는 두뇌, XGBoost는 예측 계산기, Streamlit은 모니터.

Gemini API 키 관리 방법

3개 API 키 보관 방식 비교

키어디에 보관설정 주체
TMDB 키.env 파일사용자가 직접 입력
Dify 키.env 파일사용자가 직접 입력
Gemini 키Windows 자격증명 관리자Gemini CLI 설치 시 자동 저장

Windows 자격증명 관리자란?

비유: Chrome이 사이트 비밀번호를 저장하는 바로 그 금고. 제어판 → 자격 증명 관리자 → Windows 자격 증명

Gemini CLI를 설치하고 로그인할 때 자동으로 저장된 거예요. 파일 어디에도 키가 존재하지 않음 → GitHub에 올려도 절대 노출 안 됨.

다른 파일에서 Gemini 키 쓰는 방법

방법 1 (간단): 아래 함수를 파일 위에 복사해서 붙여넣기

import ctypes, ctypes.wintypes def get_gemini_key() -> str: # Windows 자격증명 관리자에서 꺼내기 ... # ctypes로 Windows API 호출 return key api_key = get_gemini_key() model = ChatGoogleGenerativeAI(google_api_key=api_key)

방법 2 (추천): 공용 파일 에이전트/gemini_key.py 만들고 어디서든 import

from gemini_key import get_gemini_key api_key = get_gemini_key()
한 줄 요약

Gemini 키는 파일로 존재하지 않음. Windows 금고에서 실행할 때마다 꺼내서 씀.

Dify — 노코드 AI 워크플로우 플랫폼

비유: "코딩 없이 AI 워크플로우를 레고처럼 조립하는 도구"

LangGraph (코딩)Dify (노코드)
Python 코드로 노드 연결마우스로 블록을 드래그해서 연결
개발자 필요비개발자도 가능
복잡한 로직 가능빠른 프로토타입

우리 프로젝트에서 사용한 방식

고객 정보 입력 (나이, 미접속일수, 시청장르) │ ▼ Dify 워크플로우 실행 (app.dify.ai에서 만든 흐름) │ ▼ 이탈 방지 메시지 출력 "오랫동안 안 보이셨네요. 좋아하시는 드라마 새 시즌이 나왔어요!"

Python 코드에서는 API 호출 한 줄로 Dify 워크플로우를 실행해요.

Dify에서 다른 AI 키는 어디서?

Dify 사이트 설정 → 모델 공급자에 Gemini 키를 한 번만 등록해두면, 내 Python 코드는 Dify 키 하나만 가지고 있으면 돼요. 나머지는 Dify 서버가 처리.

내 Python 코드 (DIFY_API_KEY만 가짐) │ "Dify야, 워크플로우 실행해줘" ▼ Dify 서버 (Gemini 키 보관 중) │ 내부적으로 Gemini 호출 ▼ 결과를 내 코드로 반환

언제 뭘 쓰나

상황추천
복잡한 로직, 데이터 처리가 많음LangGraph (코딩)
빠르게 프로토타입 만들고 싶음Dify (노코드)
비개발자가 워크플로우를 수정해야 함Dify

08

워크플로우(Workflow)란?

"일이 처리되는 순서" 예요.

일상 예시 — 카페 커피 주문

손님이 주문 → 직원이 결제 받음 → 바리스타가 커피 만듦 → 손님 이름 호출 → 커피 전달

이 순서가 바뀌면 안 되죠. 결제 전에 커피 먼저 주면 안 되니까요.

AI 워크플로우 예시

고객 정보 입력 → 위험도 분석 → 위험도에 맞는 메시지 작성 → 완성된 메시지 출력

왜 단계를 나눠야 할까?

❌ 한 번에 시키기✅ 단계별로 시키기
"고객 분석하고 위험도 파악하고 메시지도 써줘" → 대충 만들어냄1단계: "분석해" / 2단계: "판단해" / 3단계: "써줘" → 정교한 결과
한 줄 요약

워크플로우 = AI한테 일을 시킬 때 순서대로 단계를 나눠놓은 것.

결론: 개인 프로젝트용 키는 넣어도 돼요.

안전한 이유

항목내용

공개 여부GitHub처럼 코드가 공개되는 게 아님

상황안전도
Dify 클라우드 (app.dify.ai)✅ 비교적 안전
